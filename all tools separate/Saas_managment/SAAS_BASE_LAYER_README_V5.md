## What This Dataset Is

This is a synthetic but analytically realistic base layer for a **Strategic Sourcing / SaaS Spend Management system**. It models the full contract-to-usage-to-people stack of a mid-large enterprise with ~6,000 active employees across 6 SaaS vendors.

The dataset is designed to power:
- Contract provisioning views (entitlement vs actual usage)
- True-up exposure calculations
- Shelfware and ghost license detection
- Renewal forecasting and notice deadline alerting
- Department-level spend attribution
- Optimization-first procurement workflows

It is **not** a live data extract. It is purpose-built synthetic data that behaves like real enterprise SaaS data — benchmarked against Zylo, BetterCloud, Gartner, and Productiv industry indexes.

### Schema

| Column | Type | Description |

| `vendor` | string | Vendor name |
| `sku` | string | Product name |
| `seat_type` | string | `Full` / `Contributor` / `Collaborator` — license tier |
| `contract_group_id` | string | Groups parallel chains of the same vendor+SKU+seat_type |
| `contracted_seats` | int | Seats committed in this specific Order Form |
| `unit_price` | decimal | Price per seat per month for this OF |
| `contract_start` | date | Effective start date of this OF |
| `contract_expiry` | date | End date of this OF |
| `notice_deadline` | date | Deadline to act — expiry minus notice period |
| `auto_renewal` | boolean | Whether this OF auto-renews if no action taken |
| `true_down_rights` | boolean | Whether seat reduction at renewal was negotiated |
| `measurement_method` | string | `peak` / `average` / `snapshot` — how usage is measured for billing |
| `contract_status` | string | `active` / `superseded` |
| `predecessor_of_id` | string | FK to prior OF in the same renewal chain. Null for chain starts (81 null rows — all are `contract_event_type = 'new'`) |
| `contract_event_type` | string | `new` / `renewal` / `upsell` / `amendment` |
| `seat_delta` | int | Seats added vs predecessor. Always 0 for renewals. Always positive for upsells and amendments in this dataset (no seat reductions recorded). |
| `effective_total_seats` | int | **Current total entitlement** — sum of all active OF contracted_seats for this vendor+SKU+seat_type |

### Critical Design Notes

**`contracted_seats` vs `effective_total_seats`**
`contracted_seats` is the amendment-level seat count for that specific OF. `effective_total_seats` is the cumulative active entitlement — what the company actually owns right now across all active OFs for that vendor+SKU+seat_type. Always use `effective_total_seats` for true-up math, never `contracted_seats` directly.

**Multiple active OFs per vendor+SKU+seat_type (by design)**
Some vendor+SKU+seat_type combinations have 2–3 simultaneously active OFs (e.g. Cloudora Cloud Infra Core Full has 3). All carry the same `effective_total_seats` value — the cumulative total. When joining for entitlement, deduplicate at `vendor + sku + seat_type` grain using `.first()` or `DISTINCT` on `effective_total_seats`. Do **not** sum `effective_total_seats` across multiple active OFs for the same group — it will double/triple-count.

**Contract lineage via `predecessor_of_id`**
Self-referential FK. Traces renewal chains: OF-001 → OF-002 → OF-003. `contract_group_id` groups parallel chains of the same vendor+SKU+seat_type where multiple active OFs coexist.

**`seat_delta` semantics by event type**
- `new` → equals full `contracted_seats` value (baseline); always positive
- `renewal` → always 0 (replacement, not additive)
- `upsell` → positive delta above predecessor
- `amendment` → positive delta above predecessor (only additive amendments exist in this dataset)

**`notice_deadline` is the action date, not the expiry date**
Procurement must act before `notice_deadline` — not `contract_expiry` — to avoid auto-renewal or missed negotiation windows.

**`true_up_frequency` and `true_up_date` are not stored here**
These are derived in the processing layer from contract duration and `measurement_method`. Contract duration maps to frequency: 12 months → annual, 6 months → semi-annual, 3 months → quarterly.

### Design Notes

**`email` is the join key**
HR email → `license_utilization.assigned_email`. This is the primary identity bridge across the entire dataset. Zero orphans confirmed — every license email resolves to an HR record.

**`employee_status` derivation rule**
Derived from `is_active` and `exit_date` with no ambiguity:
- `is_active = True` → `employee_status = 'active'`
- `is_active = False` and `exit_date` is not null → `employee_status = 'exited'`
- `is_active = False` and `exit_date` is null → `employee_status = 'pre-hire'`

Any row where `is_active = False` and both `exit_date` and `hire_date` are null is a data quality error. Zero such rows exist in this file.

**Pre-hire records (180 rows)**
Employees confirmed in HRIS ahead of their start date. `hire_date` falls between 2026-05-02 and 2026-07-31. These rows have `is_active = False`, null `exit_date`, null `exit_type`, null `manager_id`, and null `sub_team`. IDs run from `EMP-10239` to `EMP-10418`. Emails follow `prehire.empNNNNN@company.com` — unique across all 10,418 rows. Pre-hire rows must be excluded from ghost license detection and true-up calculations. Use `employee_status = 'pre-hire'` as the filter, not `is_active = False`, to avoid conflating pre-hires with exited employees.

**`employee_service.get_future_hires()` — primary consumer of pre-hire rows**
Filters on `employee_status = 'pre-hire'`. Supports `before_date` and `department` filters for renewal pressure forecasting. Pre-hire volume by month: 80 in May 2026, 60 in June 2026, 40 in July 2026.

**Exit type values**
The actual exit type values are `voluntary`, `layoff`, `performance`, and `retirement`. There is no `resignation` or `termination` value in this file.

**Exited employees are kept in the table**
Ghost license detection depends on cross-referencing `is_active = False` employees against active license records. Do not filter out exited employees before joining. Use `employee_status = 'exited'` (not `is_active = False`) so pre-hire rows are excluded from ghost detection.

**`exit_date` is null for active and pre-hire employees**
Handle with `pd.isna(exit_date)` or `IS NULL` in SQL. There are exactly 6,196 null exit_dates (6,016 active + 180 pre-hire).

**`manager_id` nulls are intentional**
583 rows have no `manager_id` — these are all L6 or L7 employees (senior managers and executives) who represent the top of the org tree. All 180 pre-hire rows also have null `manager_id` — no manager is assigned pre-start. Not a data quality issue in either case.

### Design Notes

**Two OF reference columns: `of_id` vs `current_of_id`**
`of_id` is the original OF against which the license was generated (may be superseded). `current_of_id` points to the current active OF after renewals — use this for renewal timing, notice deadlines, and contract lookups. Both FK cleanly to the vendor table with zero orphans.

**`effective_license_date` is validated against `of_id`, not `current_of_id`**
This date must fall within the `contract_start` → `contract_expiry` window of the original `of_id`, not the current active OF. All 27,646 rows were audited and confirmed correct — no errors found.

**`days_since_last_active` is computed from `last_active_date`, not stored independently**
The source file contained 6,932 rows where `days_since_last_active` was stale (not recomputed after `last_active_date` was updated). In v4 this field is authoritatively recomputed as `audit_date − last_active_date` for all non-null rows. `last_active_date` is the source of truth — `days_since_last_active` is always derived from it. Do not reverse-engineer `last_active_date` from `days_since_last_active`.

**All time-relative fields use audit date 2026-05-01 as reference**
The following fields are all computed relative to the audit date of 2026-05-01: `days_since_last_active`, `days_since_provisioned`, `contract_days_remaining`, `days_until_notice`. Do not recompute these against today's date unless generating a new audit snapshot.

**`tenure_days` is employee-level, not audit-date-relative**
Each employee has exactly one `tenure_days` value shared across all their license rows. It is computed from `hire_date` (active employees) or `exit_date` (exited employees) and is not recalculated at each audit. Do not recompute it from `provisioned_date` or the audit reference date.

**Null patterns are structured, not missing data**
`last_active_date`, `days_since_last_active` — null only for `license_status = 'deprovisioned'` (4,148 rows exactly). `churn_risk_score` — null only for `deprovisioned` and `ghost` statuses (10,976 rows = 4,148 + 6,828). These are intentional.

**`license_status` definitions**
- `active` — employed, provisioned, using the license
- `ghost` — exited employee whose license was never deprovisioned
- `deprovisioned` — license formally removed (last_active_date always null)
- `over_tier` — seat type is higher than job level warrants (e.g. Full license for L1)

**`seat_tier_match` vs `license_status`**
`over_tier` in `license_status` and `seat_tier_match = 'over_tier'` are equivalent. Additionally, 529 active licenses have `seat_tier_match = 'under_tier'` (employee job level exceeds seat tier) — these are not reflected in `license_status` and represent upgrade candidates, not a waste signal.

**`renewal_urgency = 'expired'`**
479 licenses across Nexaflow (261) and Cloudora (218) have `renewal_urgency = 'expired'`, meaning the associated contract has lapsed past its expiry. These include active licenses (283), ghost (116), deprovisioned (62), and over_tier (18). Flag these for immediate contract review.

**Ghost licenses are the largest cost-at-risk signal**
6,828 ghost records carry `cost_at_risk > 0`. These represent licenses the company is paying for with zero utility. Ghost licenses are distributed across all 6 vendors, with Veloxa (1,948) and Atlassify (1,817) carrying the largest volumes.

**`usage_tier` segments**
- `power` — high engagement (7,896 licenses)
- `moderate` — regular usage (6,306 licenses)
- `underutilized` — occasional usage (2,251 licenses)
- `dormant` — near-zero usage (217 licenses)
- `inactive` — no recorded activity (10,976 licenses — includes all ghost and deprovisioned)

## Join Logic

### Primary Joins

```
HR Headcount  ←→  License Utilization
hr_headcount.email  =  license_utilization.assigned_email

License Utilization  ←→  Vendor Overview (entitlement grain)
license_utilization.vendor + sku + seat_type
    →  vendor_overview[contract_status='active'].vendor + sku + seat_type
    →  DISTINCT effective_total_seats  (dedup required — see below)

License Utilization  ←→  Vendor Overview (contract/renewal grain)
license_utilization.current_of_id  =  vendor_overview.of_id
```

### Entitlement Join Pattern — DEDUPLICATION REQUIRED
Multiple active OFs can exist per vendor+SKU+seat_type (2–3 in this dataset). All carry the same `effective_total_seats` value. Always deduplicate before using:

```python
# Correct
entitlement = (
    vendor[vendor['contract_status'] == 'active']
    .groupby(['vendor', 'sku', 'seat_type'])['effective_total_seats']
    .first()
    .reset_index()
)
```

Do **not** join License Utilization to Vendor Overview on `of_id` for entitlement calculations. Join on `vendor + sku + seat_type` with the deduplicated entitlement above.

### Ghost License Detection
```python
ghosts = license_utilization[license_utilization['license_status'] == 'ghost']
# All ghost licenses join cleanly to exited employees in hr_headcount
# Zero ghost licenses are assigned to is_active=True employees
```

### True-up Exposure Calculation
```python
active_provisioned = (
    license_utilization[license_utilization['license_status'].isin(['active', 'over_tier'])]
    .groupby(['vendor', 'sku', 'seat_type'])
    .size()
    .reset_index(name='active_provisioned')
)

merged = active_provisioned.merge(entitlement, on=['vendor', 'sku', 'seat_type'], how='outer')
merged['exposure_seats'] = merged['active_provisioned'].fillna(0) - merged['effective_total_seats'].fillna(0)

# positive = over-provisioned = true-up risk
# negative = under-provisioned = shelfware
```

## Database Layer — SQLite

The three CSV files are loaded into a SQLite database at session startup. All queries throughout the processing layer, API layer, and dashboard use SQL against this database — not pandas CSV reads directly. This ensures the codebase migrates cleanly to any production database (PostgreSQL, DuckDB, Snowflake) by swapping only the connection string.

### Database File
`saas_spend.db` — portable, ships with the project, generated from CSVs at first run.

### Table Names

| CSV File | SQLite Table Name |
|---|---|
| `vendor_overview_patched_v5.csv` | `vendor_overview` |
| `hr_headcount_v2.csv` | `hr_headcount` |
| `license_utilization_v4.csv` | `license_utilization` |

### Startup Loading Pattern

```python
import sqlite3
import pandas as pd

conn = sqlite3.connect("saas_spend.db")

pd.read_csv("vendor_overview_patched_v5.csv").to_sql(
    "vendor_overview", conn, if_exists="replace", index=False)
pd.read_csv("hr_headcount_v2.csv").to_sql(
    "hr_headcount", conn, if_exists="replace", index=False)
pd.read_csv("license_utilization_v4.csv").to_sql(
    "license_utilization", conn, if_exists="replace", index=False)
```

Run once. After this all layers read from `saas_spend.db`.

### Migration Path
When shifting to production — replace `sqlite3.connect("saas_spend.db")` with the production connection. All SQL queries stay identical.

## What Comes Next — Table 4

**True-up Exposure table** is computed from these three tables. It is never raw data — it is a periodic snapshot generated by the processing layer.
